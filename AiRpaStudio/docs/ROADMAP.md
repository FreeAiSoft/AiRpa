## 1. Цели продукта и критерии «готово»

| ID | Цель | Критерий приёмки (проверяемый) |
|---|---|---|
| **Ц1** | Продукт с очень удобным интерфейсом для редактирования/создания роботов | Пользователь проходит путь «новый проект → робот → отладка → запуск», не открывая XAML руками: валидация в дизайнере с переходом к ошибке, IntelliSense и подсказки в выражениях, контекстные меню на всех сущностях, drag&drop в дереве проекта, восстановление раскладки и вкладок. Все перечисленные пункты закрыты автотестами (кроме чисто визуальных) и внесены в `docs\Vs2026_Theme_Acceptance.md`-подобный чек-лист приёмки UI |
| **Ц2** | Совместимость студии с проектами на **.NET Framework 4.7.2**, работа в **VS 2022 и VS 2026** | Студия открывает, редактирует, собирает и запускает робота из проекта, целящегося `v4.7.2`, без ручных правок; эталонный набор проектов (4.7.2 и 4.8) открывается/собирается в тесте через MSBuild **и** VS 2022, **и** VS 2026; в репозитории нет сборки, которую нельзя подключить к 4.7.2-проекту без объяснения |
| **Ц3** | Свой агент, который пишет активности XAML, + **специальные инструменты построения XAML-активностей** | Агент по текстовому запросу собирает валидный workflow через типизированные инструменты (вставка/удаление/перемещение активности, аргументы, переменные, валидация), а не через «перепиши файл целиком»; каждая мутация атомарна и откатывается через Undo дизайнера; инструменты покрыты тестами на фикстурах XAML, включая негативные сценарии |
| **Ц4** | Фичи обработки ТЗ | Загрузка ТЗ (`md/txt/docx/pdf`, изображения) → структурированная спецификация (цель, предусловия, шаги, данные, ветвления, исключения, критерии приёмки) → задачи → скелет робота; есть трассировка «пункт ТЗ ↔ элемент workflow» и отчёт о покрытии; неоднозначности закрываются вопросами пользователю |
| **Ц5** | **Полноценный оркестратор на Blazor** | Разворачивается отдельно от студии (self-hosted, Windows-служба + веб-UI) и **не требует установленной студии**: хранит роботов и их версии в виде пакетов, запускает их вручную и по расписанию на машинах-агентах, показывает прогресс (текущая активность) и логи в реальном времени, хранит историю запусков с артефактами, разграничивает роли и ведёт аудит, отдаёт API для внешнего запуска. Есть автотесты API, планировщика и раннера; сценарий «собрали пакет → запланировали → робот отработал → лог и статус в UI» проходит end-to-end |
| **Ц6** | **Компактный запускатор-планировщик (WPF)** | Одно компактное приложение: видит локальных роботов, запускает/останавливает их без студии, показывает прогресс и лог, ставит локальные расписания, живёт в трее и в автозапуске, держит локальную историю запусков. Работает offline без оркестратора; при доступном оркестраторе — берёт из него свои расписания и отдаёт статусы. Запуск робота из запускатора не открывает студию и не тянет за собой её тяжёлые зависимости |

## 2. Как читать документ

Статусы: ✅ сделано · 🟡 частично / требует аудита · ⏳ не начато · 🔴 блокер · 🗄 устарело (история).
Приоритеты: **P0** — блокирует цель, **P1** — нужно к бетe, **P2** — после альфы.

Префиксы ID: `UI-` (Ц1) · `CP-` (Ц2) · `AG-` (Ц3) · `TZ-` (Ц4) · `OR-` (Ц5, оркестратор) · `LN-` (Ц6, запускатор-планировщик) · `TD-` (тех-долг) · `TH-` (тема).

Ц1–Ц4 — это студия. Ц5 и Ц6 — **отдельные приложения** в том же решении: оркестратор (сервер + веб-UI) и запускатор-планировщик (компактный WPF-клиент). Их задачи нельзя закрывать правками студии «по месту»: общий код выносится в переиспользуемые сборки (§8.3).

## 6. Ц3 — Агент и инструменты построения XAML-активностей

Сейчас агент умеет: читать файлы/дерево/поиск, git, сборка, шелл, правка файла целиком, вопросы пользователю, сабагенты, поиск по встроенной документации. Чего нет: понимания **модели workflow** — структуры дерева, аргументов, переменных, валидации. Практически это значит, что «сгенерировать робота» агент может только переписав XAML-файл текстом, что ломает открытый дизайнер, не даёт Undo и не гарантирует валидность.

## 8. Ц5 — Полноценный оркестратор на Blazor

Отдельное приложение в `AiRpa.sln` (папка решения `Orchestrator`), которое **не требует установленной студии**: сервер + веб-UI на Blazor, машины-агенты, пакеты роботов, расписания, история. Сейчас кода нет; единственный рантайм вне студии — прототип `WorkflowHost` (`WorkflowHost\Program.cs`), который для роли раннера не годится (§3). В `TODO.txt` пункты «оркестратор» и «агент по управлению для оркестратора» до сих пор без `+`.

### 8.1. Принципы

1. **Оркестратор — не студия.** Он исполняет уже собранные пакеты роботов и не умеет редактировать XAML. Редактирование остаётся в студии (Ц1) и у агента (Ц3).
2. **Робот — это неизменяемый пакет версии.** Изменил робота → новая версия, старые запуски остаются воспроизводимыми.
3. **Всё, что делает запуск, живёт в `RpaRunner.exe`** (v4.7.2). Оркестратор и запускатор — только клиенты раннера, поэтому логика исполнения не дублируется в двух UI.
4. **Совместимость Ц2 не отменяется:** раннер и запускатор работают на 4.7.2-рантайме, контракты API — `netstandard2.0`.
5. **Один процесс — один запуск.** Никаких запусков роботов внутри процесса веб-сервера.

## 9. Ц6 — Компактный запускатор-планировщик (WPF)

### 9.1. Принципы

1. **Компактность — требование, а не пожелание:** не тянуть дизайнер WF, редакторы и студию; холодный старт — секунды, окно — одно.

3. **Offline-first:** без оркестратора приложение полностью работоспособно; связь с сервером — необязательный режим.
4. **Один экземпляр:** повторный запуск активирует уже открытое окно.

## 14. Правила ведения роадмэпа

1. Закрытие пункта: ставим `+` в `AiRpaStudio\TODO.txt` (для пунктов беклога), меняем статус в этом файле, добавляем тест/страж и указываем файлы-артефакты.
2. Новые задачи получают ID по префиксу и приоритет; «хотелки» без привязки к Ц1–Ц6 не попадают в волны 1–2 (ближайший горизонт).
3. Устаревшие планы не переписываются: в шапке ставится «🗄 заменён на `docs\ROADMAP.md` / `docs\...`».
4. Изменение целей или критериев приёмки (§1) — только вместе с явным решением владельца продукта.
5. Раз в волну: сверка беклога с кодом (`TD-08`) и обновление даты актуализации.
6. Ц5 и Ц6 не закрываются правками студии: задача `OR-*`/`LN-*` считается сделанной только в своём приложении. Общий код выносится в `Rpa.Orchestrator.Contracts` (§8.3); дублирование логики исполнения в двух UI запрещено — единственный исполнитель робота это `RpaRunner` (`OR-02`), оркестратор и запускатор только клиенты.
7. Изменение списка целей (добавление Ц7 и далее) — сначала строка в §1 с проверяемым критерием приёмки, потом задачи; задачи без критерия не заводятся.
