# Диагностика темы дизайнера WF

Набор инструментов для визуальных багов темизации: «на светлой теме остался тёмный прямоугольник»,
«после переключения темы плашка не вернулась», «текст не читается на фоне». Проверено на реальном баге
пустой активности (см. раздел «Разобранный случай»).

Код студии эти скрипты не меняют: только читают окно процесса и запускают пробник.

## Быстрый старт

```powershell
# 1) Сквозная проверка темизации на настоящем WorkflowDesigner (light → dark → light).
#    Печатает фон плиты пустой активности и число элементов на цвете чужой палитры.
powershell -ExecutionPolicy Bypass -File tools\designer-ui-diagnostics\Invoke-DesignerThemeProbe.ps1

# 2) Если баг виден в живом окне: снимок + пиксельный анализ (гистограмма, bbox, детект «рамки»).
powershell -ExecutionPolicy Bypass -File tools\designer-ui-diagnostics\Get-UiSnapshot.ps1

# 3) Привязать прямоугольник со снимка к элементам дерева.
powershell -ExecutionPolicy Bypass -File tools\designer-ui-diagnostics\Get-UiTree.ps1
```

Отчёты складываются в `tmp\ui-snapshot\` и `tmp\ui-tree\` (папка `tmp` в `.gitignore`), отчёт пробника —
в `tools\designer-ui-diagnostics\probe\bin\probe-report.txt` (`probe\bin` в `.gitignore`).

Уже снятый снимок можно разобрать повторно — без запущенной студии:

```powershell
powershell -ExecutionPolicy Bypass -File tools\designer-ui-diagnostics\Get-UiSnapshot.ps1 -ImagePath tmp\shot.png
```

## Метод: порядок шагов

1. **Пиксели, а не глаз.** Снимок окна → гистограмма: цвет, которого нет в активной палитре, — первый
   подозреваемый. В разобранном случае это был `#272727` = `StudioPalette.Dark.Surface` на светлой теме.
2. **Форма дефекта.** Для подозрительного цвета скрипт считает bounding box и сравнивает центр с
   периметром. Если центр другого цвета — это **рамка** (кольцо), а не сплошная плашка, и её толщина
   говорит о том, что закрашен `Border`, вокруг которого лежит прозрачная/белая внутренность.
3. **Привязка к дереву.** `Get-UiTree.ps1` (UI Automation, RawViewWalker) даёт ControlType, ClassName,
   AutomationId и экранные координаты. Сверка прямоугольников «снимок ↔ дерево» показывает, на каком
   уровне элемент: у `Border` шаблона может не быть UIA-пира, и тогда он виден только как разница
   размеров между родителем и ребёнком (`ActivityTypeDesigner` 420×420 внутри плиты 440×440).
4. **Механизм, а не симптом.** `Invoke-DesignerThemeProbe.ps1` гоняет на реальном `WorkflowDesigner`
   те же проходы, что и студия, и печатает, что осталось на цвете чужой палитры после каждого прохода.
   Это отделяет «шаблон WF перекрасил» от «наш темизатор не откатил».
5. **Только потом код.** Точка правки ищется в темизаторе по имени прохода (см. `WfDesignerTheme`,
   `WfThemeStyles`, `WfVisualTreeThemer`), а результат подтверждается тестами + шагом 4.

## Что внутри

| Файл | Назначение |
| --- | --- |
| `Invoke-DesignerThemeProbe.ps1` | компилирует и запускает пробник темы на настоящем дизайнере |
| `probe\DesignerThemeProbe.cs` | исходник пробника: пустая активность, проходы light → dark → light, отчёт |
| `Get-UiSnapshot.ps1` | снимок окна процесса, гистограмма цветов, bbox подозрительных цветов, детект рамки |
| `Get-UiTree.ps1` | дамп дерева UI Automation окна процесса |

Пробник не требует `InternalsVisibleTo`: `WfDesignerTheme.Apply` вызывается по рефлексии, палитры
берутся из публичного `StudioPalette`. Запуск идёт из папки тестов — там лежат все зависимости и
`.config` с binding redirect'ами (без них WF падает на `ICSharpCode.AvalonEdit` в `ImportDesigner`).

## Разобранный случай: чёрный прямоугольник у пустой активности

Симптом: светлая тема → пустая XAML-активность («Перетащите сюда действие») → тёмная тема → обратно
светлая. Тема применяется, но вокруг подсказки остаётся чёрная рамка толщиной ~15 px.

Что показали инструменты:

* `Get-UiSnapshot.ps1`: кольцо цвета `#272727` в прямоугольнике 622..1060 × 361..801, внутренность
  `#FFFFFF`, ширина кольца 11–12 px. `#272727` в светлой палитре отсутствует — значит, это `Dark.Surface`.
* `Get-UiTree.ps1`: `ActivityTypeDesigner` 420×420 стоит на 10 px внутри невидимого в UIA элемента
  440×440 — это плита `Border` шаблона пустой активности.
* `Invoke-DesignerThemeProbe.ps1`: до фикса проход `LIGHT AGAIN` показывал `плита: 440x440
  background=#FF272727`; после фикса — `#FFFFFFFF`, счётчики «фон/рамка/текст чужой палитры» по нулям.

Причина: `WfDesignerTheme.ReplaceWorkflowDefaultColors` перекрашивал кисти только по точному значению
дефолта WF (`#FFFFFF`, `#E9ECEE`, `#D0D7E2`, `#1B293E`). После первого прохода дефолт уже подменён на
цвет палитры, которого в списке нет, — поэтому обратный проход не срабатывал никогда. Исправление:
`WithStalePaletteColour` добавляет в список замены цвет того же токена противоположной палитры
(`Surface → Surface`, `SeparatorStrong → SeparatorStrong`, `Foreground → Foreground`).

## Ограничения

* Снимок требует, чтобы окно было видно на экране: `CopyFromScreen` не снимает перекрытые/свёрнутые окна.
* Шаг сканирования пикселей 2 px: точные координаты кромки ±1 px, для поиска плашек и рамок достаточно.
* Пробник рассчитан на .NET Framework 4.8 и WF из поставки студии; собирается Roslyn `csc.exe` из
  Visual Studio (пути поиска — в `Find-RoslynCsc`).

## Что печатает пробник про активности (обновление)

Помимо плиты пустой активности и кнопок шапки, отчёт содержит два новых блока:

* `активности: N` — для каждой активности (до четырёх): тип, подпись, размер, `bg`/`border`/`fg` самой
  активности и её шаблонных элементов (`Grid` плиты, `Border` заголовка, `Rectangle` рамки, глифы), цвета
  текстов и контролы внутри с указанием, ОТКУДА пришёл стиль: локальный, словарь приложения
  (MaterialDesign) или WF/система. Именно так пойманы оба регресса — «активность осталась белой в тёмной
  теме» и «`CheckBox` внутри активности получил стиль MaterialDesign 29×29».
* `СЛОВАРИ ЦВЕТОВ WF` — содержимое кэша `CachedResourceDictionaryExtension` и
  `WorkflowDesignerColors.DefaultColors`: какие кисти там лежат, `IsFrozen` и можно ли их перекрасить.
  Вывод, на котором построен `WfActivityTheme`: кисти **заморожены**, а сам словарь после загрузки
  шаблонов становится **read-only** (`InvalidOperationException` на записи), поэтому тема ставится
  локальными значениями на элементы шаблона, а не правкой WF-словаря.

Сценарии: пустая активность (`ActivityBuilder`), workflow `Sequence + WriteLine + вложенная Sequence` и
кастомный дизайнер (`Activities.Debug.Logger`, внутри — `ActivityTop` с `CheckBox`). В каждом сценарии
проходы `DARK (первое включение)` → `LIGHT` → `DARK AGAIN`: именно «первое включение тёмной темы» и
показывало белые активности.

Хост пробника собирается вручную (`BundledTheme` + `MaterialDesign2.Defaults.xaml` + `StudioTheme.xaml` +
`StudioScrollBar.xaml` и `AppSettings.ApplyTheme`): без ресурсов `App.xaml` неявные стили MaterialDesign
не поднимаются, и половина дефектов (кнопки шапки шириной 34, «материальный» чекбокс) не воспроизводится.
`App.xaml` студии не поднимается намеренно — его `Startup` создаёт `MainView`.

## Режимы темизации: прежний и «кэш словаря WF»

Студия ставит словарь палитры в кэш шаблонов WF (`WfColorResourcesOverride.TryInstall` в `App.xaml.cs`) —
в этом режиме `WfDesignerTheme.ReplaceWorkflowDefaultColors` выключен, и часть дефектов видна **только**
здесь. Пробник по умолчанию проверяет прежний режим, а режим кэша включается аргументом `cache`:

```powershell
powershell -ExecutionPolicy Bypass -File tools\designer-ui-diagnostics\Invoke-DesignerThemeProbe.ps1 -ProbeArgs cache
```

В отчёте появляется строка `=== РЕЖИМ ТЕМИЗАЦИИ: … ===`, а также блок `поверхность …` с кистями
`designerPresenterBorder` / `scrollableContent` / `scrollViewerContent` / `designerViewGrid`, цепочка
предков до окна и признак кисти: `frozen static` (обычная кисть палитры) или `not-frozen bound`
(связанная кисть `WfColorResourcesOverride`, меняется без обхода дерева).

## Разобранный случай: белая полоса вокруг активностей после light → dark

Симптом: студия только что загрузилась (тёмная тема) → переключение на светлую проходит нормально →
возврат в тёмную, и вокруг активностей остаётся **белый фон**, хотя сами активности перекрашены.

Что показал пробник в режиме `cache` (до исправления):

* `DARK AGAIN`: `поверхность designerViewGrid: #FFFFFFFF frozen static [Local]` — на полосе остался
  цвет светлой палитры, хотя в проходе `DARK (первое включение)` там было `#FF272727`;
* `фон чужой поверхности: 5` — `Grid#designerViewGrid 984x670`, `Grid#bottomPanel`,
  `ArgumentDesigner#arguments1`, `VariableDesigner#variables1`, `ImportDesigner#imports1`. В прежнем
  режиме тот же сценарий давал `0`: там белый дефолт подменяет `ReplaceWorkflowDefaultColors`, а в
  режиме кэша этот проход выключен.

Причина: полосу красят несколько подпроходов (`WfDataGridTheme.PaintHost` — хосты таблиц,
`WfVisualTreeThemer` — корень документа, `WfActivityTheme` — плиты), и в сторону тёмной темы ни один из
них не узнавал белый: проверка «цвет входит в активную палитру» отбрасывала его, потому что в тёмной
палитре чистый белый объявлен как `CloseHoverForeground`. В сторону светлой все проходы срабатывали —
отсюда односторонность бага.

Исправление: `WfThemeStyles.TryMapStalePaletteColour` сверяется только с токенами площади и текста
(`WfThemeStyles.BackgroundTokens`), а у поверхности дизайнера есть собственный последний проход
`WfDesignerTheme.RepaintSurfaceBand` («цвет противоположной палитры → `Surface`»; внутрь
`WorkflowViewElement` и `AdornerLayer` не заходит, пользовательские кисти не трогает).

После исправления: `поверхность designerViewGrid: #FF272727` и `фон чужой поверхности: 0` в `DARK AGAIN`,
причём счётчики `DARK (первое включение)` и `DARK AGAIN` совпадают во всех трёх сценариях — это и есть
инвариант «порядок переключений не важен». Остаточные `Path 16x10` в счётчике сценариев с активностями —
белые глифы шаблонов WF внутри активностей, они одинаковы в обоих тёмных проходах и к переключению темы
отношения не имеют. Юнит-стражи — `AiRpaStudio.Tests\WfDesignerSurfaceTests.cs`.
