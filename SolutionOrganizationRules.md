# Правила организации решения (context-aware)

> Документ-чек-лист. Применяется **по запросу** для проверки соответствия решения
> целям «ускорение разработки» и «снижение шума в контексте агента».
> Каждое правило сформулировано как проверяемое утверждение с критериями
> соответствия (✅ / ⚠️ / ❌).

---

## 0. Цель и границы применения

Организация `AiRpa.sln` влияет на размер «рабочего набора» агента: сколько файлов
и символов ему нужно прочитать для задачи и сколько раз он вынужден выяснять,
«где что лежит». Правила ниже направлены на то, чтобы границы между проектами были
явными, а контекст поднимался лениво и только по делу.

Границы применения:

- **Обязательно** — для новых проектов и новых модулей.
- **Ориентир при рефакторинге** — для существующего кода. Legacy-проекты
  (`.NET Framework 4.8`, WPF, AvalonDock/AvalonEdit и т.п.) не демонтируются
  одномоментно: правило применяется тогда, когда модуль уже меняется по другой причине.

---

## П1. Границы по контексту, а не только по слоям

**Утверждение.** Модуль с явным контрактом (интерфейсы, DTO, события) можно понять
и менять, не читая остальные проекты. Слоистость ради слоистости, наоборот, заставляет
агента читать 3–4 проекта ради одной фичи.

**Критерии соответствия:**

- [ ] Общие контракты (интерфейсы, DTO, события/команды) вынесены в отдельный
      контрактный проект с минимумом зависимостей.
- [ ] Реализация живёт в модуле и зависит от контракта, а не наоборот.
- [ ] Нет ссылок «модуль → модуль» напрямую, минуя контракт.
- [ ] Для задачи «поправь X в модуле Y» агенту достаточно прочитать сам модуль Y
      и его контракт; читать всю Infrastructure/API не требуется.
- [ ] Контракт стабилен и явно описан (имена, типы, семантика), а не выводится
      из деталей реализации.

---

## П2. Иерархические инструкции агента вместо одного монолита

**Утверждение.** Один огромный корневой файл правил загружается в каждый запрос.
Специфику проекта нужно держать в файлах рядом с проектом, чтобы не платить за неё
в контексте других задач.

**Критерии соответствия:**

- [ ] Корневой файл содержит только общее: стек, команды сборки/тестов,
      глобальные соглашения по именованию, версии TFM.
- [ ] Специфика проекта вынесена в проектные файлы инструкций
      (например, `Infrastructure/AGENTS.md`, `AiRpaStudio/AGENTS.md`), а не в корень.
- [ ] Проектные файлы не дублируют корневые правила, а дополняют их.
- [ ] При работе внутри проекта агент не обязан поднимать правила других проектов.

---

## П3. Изоляция «шумных» артефактов

**Утверждение.** `bin/`, `obj/`, `*.Designer.cs`, `Migrations/`, сгенерированные
клиенты создают шум и должны быть изолированы от навигации по умолчанию.

**Критерии соответствия:**

- [ ] Сгенерированный код вынесен в отдельные папки/проекты и явно помечен.
- [ ] Инструменты навигации (поиск символов, Roslyn-запросы) по умолчанию
      **не** возвращают символы из сгенерированных файлов.
- [ ] `bin/` и `obj/` исключены из системы контроля версий (`.gitignore`).
- [ ] Агент может отличить «код, который можно менять» от «кода, который генерируется»
      без чтения самих сгенерированных файлов.

---

## П4. Тесты — отдельно и лениво

**Утверждение.** Тесты должны лежать отдельно от продуктового кода и подгружаться
в контекст только тогда, когда задача явно связана с тестированием.

**Критерии соответствия:**

- [ ] Тестовые проекты выделены в отдельные проекты (по модулям при необходимости).
- [ ] Для задач типа `implement` / `fix` тестовые проекты **не** входят в стартовый контекст.
- [ ] Для задач типа `test` / `verify` тестовые проекты **входят** в стартовый контекст.
- [ ] Тесты не читаются «на всякий случай» при правке продуктового кода.

---

## П5. Модульность только с сильными контрактами

**Утверждение.** Дробление полезно только при наличии явных и стабильных контрактов.
Слишком мелкое дробление без контрактов увеличивает число «переходов» между проектами
и съедает токены на сборку картины.

**Критерии соответствия:**

- [ ] Каждый выделенный модуль имеет явный контракт (интерфейсы, DTO, схемы событий).
- [ ] Нет модулей-«пустышек» без контракта, существующих только ради слоистости.
- [ ] Понимание одной фичи не требует транзитивных переходов через 3+ проекта без контракта.
- [ ] Число проектов не растёт быстрее, чем число явных контрактов.

---

## Возражения и дополнения к исходным тезисам

1. **Иерархия инструкций — только `AGENTS.md`.** Правило П2 применяем к иерархии
   `AGENTS.md`: корневой файл содержит глобальные правила, специфика вынесена в
   проектные `AGENTS.md` (`AiRpaStudio`, `RPA.NuGet`, `Rpa.Workflow.Runtime`,
   `Agent.Core`).

2. **Legacy-проекты не трогаем без причины.** Полная реструктуризация WPF/.NET
   Framework-решения под чистую модульность рискованна и не окупается немедленно.
   Правила обязательны для новых модулей и применяются к существующему коду только
   в момент, когда он и так меняется.

3. **Изоляция шума не всегда требует новых проектов.** Часто дешевле исключить
   сгенерированные файлы из навигации на уровне инструментов (Roslyn/поиск), чем
   плодить проекты. П3 не требует «исключить из сборки» — сгенерированный код нужен
   сборке; требуется исключить его из контекста навигации по умолчанию.

4. **«80–90% экономии» — эмпирика, а не норматив.** На маленьких модулях издержки
   на «переходы» могут превысить выгоду. Поэтому первичен критерий сильного
   контракта (П5), а не сам факт дробления.

5. **Ленивая загрузка тестов требует конфигурации агентского цикла.** Сам факт
   отдельного проекта тестов (уже есть `AiRpaStudio.Tests`) не отключает их
   из контекста автоматически. Нужно явно зафиксировать правило включения/исключения
   тестов по типу задачи — это дополнение к П4.

## Как применять

1. При проверке соответствия пройтись по чек-боксам П1–П5 и зафиксировать статус.
2. Нарушения фиксировать как «⚠️ частично» или «❌», а не молча.
3. Исправлять по приоритету: сначала дешёвые правки (иерархия инструкций, исключение
   шума из навигации), затем — контрактные границы при ближайшем рефакторинге модуля.
4. Данный документ сам является правилом и может пересматриваться по мере изменения
   архитектуры решения.
