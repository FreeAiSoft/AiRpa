# Правила организации решения (context-aware)

> Документ-чек-лист. Применяется **по запросу** для проверки соответствия решения
> целям «ускорение разработки» и «снижение шума в контексте агента».
> Каждое правило сформулировано как проверяемое утверждение с критериями
> соответствия (✅ / ⚠️ / ❌).

---

## 0. Цель и границы применения

Организация `AiRpa.sln` влияет на размер «рабочего набора» агента: сколько файлов
и символов ему нужно прочитать для задачи и сколько раз он вынужден выяснять,
«где что лежит». Правила ниже направлены на то, чтобы границы между проектами были
явными, а контекст поднимался лениво и только по делу.

Границы применения:

- **Обязательно** — для новых проектов и новых модулей.
- **Ориентир при рефакторинге** — для существующего кода. Legacy-проекты
  (`.NET Framework 4.8`, WPF, AvalonDock/AvalonEdit и т.п.) не демонтируются
  одномоментно: правило применяется тогда, когда модуль уже меняется по другой причине.

---

## П1. Границы по контексту, а не только по слоям

**Утверждение.** Модуль с явным контрактом (интерфейсы, DTO, события) можно понять
и менять, не читая остальные проекты. Слоистость ради слоистости, наоборот, заставляет
агента читать 3–4 проекта ради одной фичи.

**Критерии соответствия:**

- [ ] Общие контракты (интерфейсы, DTO, события/команды) вынесены в отдельный
      контрактный проект с минимумом зависимостей.
- [ ] Реализация живёт в модуле и зависит от контракта, а не наоборот.
- [ ] Нет ссылок «модуль → модуль» напрямую, минуя контракт.
- [ ] Для задачи «поправь X в модуле Y» агенту достаточно прочитать сам модуль Y
      и его контракт; читать всю Infrastructure/API не требуется.
- [ ] Контракт стабилен и явно описан (имена, типы, семантика), а не выводится
      из деталей реализации.

---

## П2. Иерархические инструкции агента вместо одного монолита

**Утверждение.** Один огромный корневой файл правил загружается в каждый запрос.
Специфику проекта нужно держать в файлах рядом с проектом, чтобы не платить за неё
в контексте других задач.

**Критерии соответствия:**

- [ ] Корневой файл содержит только общее: стек, команды сборки/тестов,
      глобальные соглашения по именованию, версии TFM.
- [ ] Специфика проекта вынесена в проектные файлы инструкций
      (например, `AiRpaStudio/AGENTS.md`, `RPA.NuGet/AGENTS.md`, `Rpa.Workflow.Runtime/AGENTS.md`, `Agent.Core/AGENTS.md`), а не в корень.
- [ ] Проектные файлы не дублируют корневые правила, а дополняют их.
- [ ] При работе внутри проекта агент не обязан поднимать правила других проектов.

---

## П3. Изоляция «шумных» артефактов

**Утверждение.** `bin/`, `obj/`, `*.Designer.cs`, `Migrations/`, сгенерированные
клиенты создают шум и должны быть изолированы от навигации по умолчанию.

**Критерии соответствия:**

- [ ] Сгенерированный код изолирован от ручной правки: вынесен в отдельные папки/проекты либо исключён из навигации на уровне инструментов; из сборки не исключается.
- [ ] Инструменты навигации (поиск символов, Roslyn-запросы) по умолчанию
      **не** возвращают символы из сгенерированных файлов.
- [ ] Изоляция сгенерированного кода достигается на уровне навигации (Roslyn/поиск) и не требует обязательного вынесения в новые проекты.
- [ ] `bin/` и `obj/` исключены из системы контроля версий (`.gitignore`).
- [ ] Агент может отличить «код, который можно менять» от «кода, который генерируется»
      без чтения самих сгенерированных файлов.

---

## П4. Тесты — отдельно и лениво

**Утверждение.** Тесты должны лежать отдельно от продуктового кода и подгружаться
в контекст только тогда, когда задача явно связана с тестированием.

**Критерии соответствия:**

- [ ] Тестовые проекты выделены в отдельные проекты (по модулям при необходимости).
- [ ] Для задач типа `implement` / `fix` тестовые проекты **не** входят в стартовый контекст.
- [ ] Для задач типа `test` / `verify` тестовые проекты **входят** в стартовый контекст.
- [ ] Тесты не читаются «на всякий случай» при правке продуктового кода.
- [ ] Правило включения/исключения тестов по типу задачи зафиксировано явно в конфигурации агентского цикла.

---

## П5. Модульность только с сильными контрактами

**Утверждение.** Дробление полезно только при наличии явных и стабильных контрактов.
Слишком мелкое дробление без контрактов увеличивает число «переходов» между проектами
и съедает токены на сборку картины.

**Критерии соответствия:**

- [ ] Каждый выделенный модуль имеет явный контракт (интерфейсы, DTO, схемы событий).
- [ ] Нет модулей-«пустышек» без контракта, существующих только ради слоистости.
- [ ] Понимание одной фичи не требует транзитивных переходов через 3+ проекта без контракта.
- [ ] Число проектов не растёт быстрее, чем число явных контрактов.
- [ ] Дробление оправдано сильным контрактом, а не самим фактом разделения; на малых модулях издержки переходов не превышают выгоду.
- [ ] Legacy-проекты (WPF/.NET Framework, внешние AvalonDock/AvalonEdit) не дробятся без причины; правила применяются к ним при их изменении.

---

## П6. Документация классифицируется по «авторитету», а не по папкам

**Утверждение.** Планы, решения, заметки — разные типы знаний с разной степенью доверия.
Смешивать их в одной куче опасно: агент может прочитать устаревший план и принять его за
текущую истину.

**Критерии соответствия:**

- [ ] Каждый документ (или секция) имеет тег статуса: `canonical` / `planning` / `historical`.
- [ ] `canonical` — актуальные контракты, ADR со статусом `accepted`, текущие планы со
      статусом `active`; агент может на это опираться.
- [ ] `planning` — черновики, предложения, roadmap; читаются только когда задача явно
      про планирование.
- [ ] `historical` — старые решения, завершённые планы; не загружаются по умолчанию,
      только по явному запросу.
- [ ] Устаревшие источники помечаются статусом, а не прячутся: они видны, но не входят
      в автоматический контекст.

---

## П7. «Карта» документации компактна и стабильна

**Утверждение.** Агент не должен сканировать директории документации через Grep или чтение
файлов. Вместо этого даётся индексный файл (например, `docs/INDEX.md`), который перечисляет,
что где лежит, со статусом и кратким описанием.

**Критерии соответствия:**

- [ ] Есть единый индекс документации (`docs/INDEX.md`), а не только разрозненные папки.
- [ ] Индекс короткий (ориентир — до ~5000 токенов, как в `llms.txt`) и стабильный,
      чтобы не ломать prompt cache.
- [ ] Индекс содержит только маршрутизацию — путь + статус + краткое описание;
      не дублирует содержание документов.
- [ ] Индекс читается один раз в начале сессии и используется для навигации без загрузки
      самих документов.
- [ ] Маршруты явные: «планы по модулю X → `docs/plans/x/`, только активные»,
      «архитектурные решения → `docs/adr/`, фильтр по статусу `accepted`».

---

## П8. Документация загружается только под конкретную задачу

**Утверждение.** Принцип progressive disclosure: всегда загружено только необходимое,
остальное — по требованию. Для документации это значит — стартовый контекст из индекса
и 1–2 канонических документов, напрямую связанных с задачей.

**Критерии соответствия:**

- [ ] При старте задачи агент получает только индекс и, при необходимости, 1–2
      канонических документа, связанных с задачей (например, контракт модуля, который
      собирается менять).
- [ ] Планы и заметки подгружаются только для задач типа «спланируй» / «посмотри, что
      решено по X» или по явному запросу агента.
- [ ] Исторические документы — только по явному запросу пользователя.
- [ ] Есть инструмент `get_doc_context(task)` / `route_docs(task)`, возвращающий
      релевантные секции с указанием источника, а не целые файлы.

---

## П9. Документация не читается через файловые инструменты

**Утверждение.** Если у агента есть Read/Grep по директориям документации, он рано или
поздно прочитает лишнее. Документация исключается из области файловых инструментов и
доступна только через специализированные инструменты с фильтрацией по статусу и возвратом
фрагментов.

**Критерии соответствия:**

- [ ] Директории документации исключены из области файловых инструментов Read/Grep агента.
- [ ] Доступ к документации — только через структурированный поиск по индексу с фильтрами
      (статус, модуль, тип документа).
- [ ] Инструменты возвращают ограниченные фрагменты (bounded excerpts) с точными
      locations, а не целые файлы.
- [ ] Тот же принцип, что с кодом: для кода — Roslyn-запросы, для документации —
      структурированный поиск, а не чтение файлов.

---

## П10. Внешние источники документации — только явно и с provenance

**Утверждение.** Планы и заметки часто живут в Confluence, Notion или отдельном
репозитории. Внешние источники достаются только по явному запросу и с указанием
происхождения; в автоматический контекст не включаются.

**Критерии соответствия:**

- [ ] Есть настройка «какие внешние источники разрешены» (явный opt-in).
- [ ] Внешние источники не включаются в автоматический контекст.
- [ ] Для запроса внешних источников есть отдельный инструмент.
- [ ] Каждый внешний источник имеет тег authority и provenance (откуда взят).

---

**Итог по документации.** Для разбросанной документации работает та же логика, что и для
кода: индекс вместо сканирования, статус вместо доверия по умолчанию, фрагменты вместо
целых файлов, загрузка по требованию вместо предзагрузки. Преимущество VS-расширения в том,
что маршрутизацию можно встроить как первоклассный инструмент в цикл агента, а не полагаться
на то, что модель «догадается» не читать лишнее. Правила П6–П10 реализуются через настройку инструментов и индексного файла, а не через одномоментную реструктуризацию заметок; существующие заметки индексируются лениво при их изменении.

## Как применять

1. При проверке соответствия пройтись по чек-боксам П1–П10 и зафиксировать статус.
2. Нарушения фиксировать как «⚠️ частично» или «❌», а не молча.
3. Исправлять по приоритету: сначала дешёвые правки (иерархия инструкций, исключение
   шума из навигации, индекс и теги статусов документации, исключение документации из
   файловых инструментов), затем — контрактные границы при ближайшем рефакторинге модуля.
4. Данный документ сам является правилом и может пересматриваться по мере изменения
   архитектуры решения.
